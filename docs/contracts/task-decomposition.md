# Управление планом одной задачи

Tracker владеет планом, историей и операциями сохранения. UI и CLI используют
один API; Workflow не хранит вторую копию. Внедрение в установленный SDLC2 и
реальный Architect handoff проверяются отдельно от исходников.

Маршруты используют существующий строгий central admission и стабильный
`TASKTRACKER_SDLC__INSTANCE_ID` установки. Отсутствие SDLC binding у обычной
задачи не требует запуска агента. При отключённом модуле SDLC самой установки
owner API отвечает 503, а не выдаёт ошибку конфигурации за пустой план.

План содержит `overview`, `source` и `sections`. `source=null` допускается,
если у задачи ещё нет требований SDLC. Иначе нужны точные
`requirements_revision` и `requirements_hash`; optional `analysis_result_id`
может ссылаться только на результат Analyst той же задачи и требований.
Порядок массива — порядок разделов. Раздел содержит UUID `id`, `title`,
`description` с ожидаемым результатом, `criteria` и `requirements`.
У разделов нет выполнения, отдельных назначений, стадий и поставок.

## API

| Операция | Маршрут после `/api/v1/issues/{uuid}/decomposition` |
|---|---|
| Текущий план, актуальные требования и ограничения редактирования | `GET` |
| Атомарное сохранение всего плана | `POST` |
| Метаданные редакций от новых к старым | `GET /revisions?limit=20&before=N` |
| Неизменяемая редакция целиком | `GET /revisions/{revision}` |
| Результат своей исходной операции | `GET /operations/{key}` |

История использует strict `before`, limit 1..100 и `next_before`; она не выдаёт
все тексты планов одним ответом. Все ответы `no-store`. Отсутствующий план —
`200 {plan:null,...}`, неизвестная редакция/операция — 404. Нет права — 403,
неверное содержание — 422, изменённый CAS/требования/назначение — 409.

Команда создания (вымышленные ID):

```json
{
  "expected_revision": 0,
  "idempotency_key": "plan:initial",
  "reason": "",
  "fence": null,
  "content": {
    "overview": "Расширяем существующие профиль, API и форму без нового сервиса.",
    "source": null,
    "sections": [{
      "id": "11111111-1111-4111-8111-111111111111",
      "title": "Сохранение предпочтений",
      "description": "Сохранять выбор пользователя в существующем профиле.",
      "criteria": "Unit и PostgreSQL: запись, повторное чтение, отказ чужому пользователю.",
      "requirements": "R1 — сохранение; R2 — доступ только владельцу"
    }]
  }
}
```

`expected_revision=0` создаёт первую редакцию. Изменение существующего плана
требует текущую revision и непустую причину. Точный no-op не создаёт редакцию.
Ответ операции содержит hash исходной команды, `changed` и сохранённую редакцию.
Одинаковый ключ с другим payload отвергается. Повтор и readback возвращают
исходный результат, даже если план уже получил следующую редакцию.

Заголовок раздела и порядок можно менять, сохраняя UUID. Удалённый UUID остаётся
в истории и не возвращается в текущий план. Новому разделу нужен новый UUID.
План ограничен 100 разделами и 1 MB сериализованного содержания; все поля
содержательные, без NUL. Точные ограничения полей проверяются сервером.

## Права и конкурентность

Человек читает по текущему доступу к задаче и редактирует по обычному edit gate.
Human PAT требует write scope для записи. Активное изменяющее назначение PM или
delivery блокирует человеческую правку; чтение показывает причину. Архивные
проекты остаются только для чтения. Отзыв membership/account/space не сохраняет
права за счёт истории или старого результата операции.

Configured machine читает только при текущем назначении на эту задачу. Запись
разрешена текущему работающему Architect со всеми четырьмя полями `fence`:
assignment, execution, agent и assignment version. Прочие роли/legacy grants
не получают запись. Проверяются текущие требования и принадлежность анализа.
Existing namespace, owner application admission и request commit clock сохраняются.

Блокировка issue сериализует первую запись, CAS, требования и ACL с существующими
Tracker writers. История и операция записываются одной транзакцией. Новые таблицы
используют существующие ordinary-content/native-task guards и commit deadline.
Сохранение не изменяет задачу, SDLC, подтверждение владельца, отчёт или приёмку.

## UI и восстановление

Обычная карточка открывает постоянный план. Dev-примеры остаются изолированными
по явному флагу. Действующие общие компоненты Base задают форму и раскрытия.
Разделы свёрнуты; URL с UUID раскрывает соответствующий раздел. Удалённая ссылка
объясняется и отправляет к прежним редакциям по номеру плана.

Черновик остаётся при переключении вкладок, ошибки оставляют ввод. Конфликт
показывает актуальный план отдельно и требует явного продолжения. Никакого
автоматического восстановления старого плана нет. После неизвестного ответа
клиент сохраняет исходную команду и сначала читает её operation; при 404 может
повторить только ту же команду. Более новый ввод не очищается старым ответом.

## Входы и результат Architect

Configured context аддитивно возвращает `previous_result_id` принятого результата
предыдущей роли и `selected_source_policy` из immutable выбора задачи. Новых таблиц
и подстановки текущей project policy нет. Отсутствующие значения не объявляются
готовыми входами; для Architecture отсутствие выбранного источника — 503.
Противоречивый hash/namespace выбранной политики — 409, ошибка storage сохраняется.
Анализ читается существующей командой `sdlc result read`, исходники — Forge
`repository tree/blob` с точным base_commit. Чтение metadata не даёт Git-write.

Для сохранённого плана новый Architect result использует существующий
`design: ArtifactReceipt`: reference `/api/v1/issues/{task}/decomposition/revisions/{n}`,
sha256 равен content_sha256 этой редакции. Tracker проверяет существование,
task/revision/hash и совпадение требований при proposal и Complete. Старые
текстовые artifacts задач без плана сохраняют совместимость. Exact-key replay
возвращает исходный proposal; поздняя правка плана не подменяет его редакцию.
Developer и проверяющие читают ссылку принятого результата, а не текущий plan head.

Подключение установленного Architect и прогоны модели с инструментами проверяются
отдельно от repository fixtures. Отдельное обязательное человеческое
согласование технического плана не добавляется. Изменения бизнес-требований
по-прежнему принадлежат PM и владельцу. Готовность Workflow/Advisor не выводится
из успешного сохранения плана.
