# Передача фоновой находки в Tracker

Статус: целевой контракт 2026-11-08; API и runtime ещё не заявлены готовыми.
Требования владельца интерфейса:
[Fleet — Фоновые задачи](https://github.com/FerrPOINT/fleet-control/blob/feat/background-tasks-20261108/docs/BACKGROUND_TASKS.md).

Фоновые процессы, расписания, находки и project-bound сессии принадлежат Fleet.
Workflow исполняет профессии без предварительной Tracker-задачи. Tracker не
создаёт Task для запуска поиска и не владеет отдельной очередью фонового анализа.

Человек выбирает точную редакцию находки и действие «В драфт» или «В бэклог».
Материал содержит название, описание, ожидаемый результат, критерии и evidence.
Поиск багов становится Bug, рефакторинг — Task. Цель Draft — дальнейшая работа PM,
цель Backlog — работа аналитика. Проверка прав и обязательных полей проекта
выполняется Tracker; членство в Fleet не выдаёт дополнительных полномочий.

Это новый источник создания задачи, а не фиктивное завершение PM и не обход
штатной модели требований. Нельзя подставить вымышленное owner confirmation,
Workflow terminal или изменить stage обычным generic patch. Реальный owner API
создания и маршрутизации требуется реализовать и проверить на точном кандидате.

Команда привязана к источнику Fleet, проекту, finding ID, редакции материала,
намерению Draft/Backlog и исходному ключу операции. Проверяется актуальный
человеческий доступ. Точный replay возвращает прежнюю задачу; конфликт материала
не создаёт новую. Unknown outcome читается по исходной операции. Нельзя требовать
одной транзакции между БД Fleet и Tracker: сохранённая задача остаётся в Tracker,
а её связь и результат доставки восстанавливаются во Fleet.

Недостающие обязательные поля показываются человеку в интерфейсе находки.
Они не заполняются вымышленными значениями; частичная передача не объявляется
успехом. До успешного создания материал остаётся находкой.

«Не делаем» с обязательным комментарием хранит Fleet и учитывают фоновые агенты.
Они не отменяют решение и не редактируют Tracker-задачи. Повторное обнаружение
дополняет ту же находку. Незавершённая связанная задача не порождает дубль;
возврат проблемы после завершённой позволяет человеку создать новую связанную
задачу с новым намерением, сохраняя прежние IDs и историю.

Прежние незавершённые Bug Search intake/авторегистрация/автоисправление/специальная
verification заменены этой моделью. Обычный SDLC созданной человеком задачи,
применённые миграции и исторические receipts сохраняются. Ни документация,
ни будущая source-реализация не означают включение расписания или rollout.
