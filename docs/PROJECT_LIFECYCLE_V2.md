# Независимый архив проекта

Статус: source-кандидат единого пространства; не установлен. Полные route/machine/
execution guards и общая приёмка нужны до включения UI/политики.

Tracker владеет `projects.archived_at` и `project_lifecycle_revision`, отдельно
от состояний пространств и ревизии M:N. Пространство A может быть архивным, а
проект A+B — доступным для разрешённой работы через активное B. Независимый архив
самого проекта делает его содержимое доступным только для чтения. Восстановление
A либо B не снимает этот архив. Каталог, связи, проекты и документы не удаляются.

## API и полномочия

`GET /api/v2/projects/{project_key}/lifecycle` возвращает строгий ProjectLifecycle:
schema_version1, явный ProjectRef, revision, archived. Нужен допуск чтения проекта.
Это metadata, не разрешение на запись и не подтверждение остановки задания.

`PUT` того же пути принимает operation_id, expected_revision, archived. Нужны
центральный допуск, product write scope, действующая роль владельца и разрешённое
активное пространство из связей проекта. Скрытое активное B не открывает запись
пользователю, допущенному только к архивному A. Восстановление использует этот
отдельный owner port; обычные изменения архивного проекта остаются закрыты.

Изменение проверяет владельца и локальную активность под блокировками. Порядок:
original operation key → Project → локальный profile/shared header → отсортированный
catalog. Ожидание не продлевает исходный permit; фактическое состояние catalog
после ожидания имеет приоритет над старым положительным подтверждением.
Ревизия меняется только при изменении собственного archive state. No-op сохраняет
ревизию, но имеет durable receipt с первоначальным ключом. Commit guard отклоняет
и no-op receipt после исходного срока.

Точный повтор возвращает фактическое текущее состояние. Старый archive-запрос
после более позднего восстановления не архивирует проект снова. UI должен
показывать возвращённое состояние, а не сообщать о повторном применении намерения.
Тот же ключ с другим payload/actor/project — конфликт. Новая команда со старой
ревизией — конфликт. Ключ не сбрасывается после transport timeout.

## SQL и совместимость

Новая аддитивная миграция сохраняет старые checksums и receipts. Отдельные SQL
барьеры защищают основное содержимое/связи проекта от stale saves и прямой записи
после архива. Разрешённая lifecycle-транзакция меняет только два своих поля;
операционный GUC локален транзакции и сверяется с исходным receipt. Произвольное
снятие archived_at не считается восстановлением. Обычный Project.save не пишет
эти поля и не может неявно снять архив старым DTO.

Новая версия прежнего namespace guard допускает только этот узкий receipted
переход. Историческая 0090 не переписывается. Полный переход всех остальных
legacy/machine writes к общему admission пока не закрыт этим частичным этапом.

Старый DELETE проекта с canonical links возвращает явный отказ
`linked_project_requires_archive`; операция не превращается в архивирование
молча. Несвязанный legacy проект до общей активации сохраняет прежний сценарий.
После активации проекты обязаны иметь пространство. История outbox/links/receipts
не стирается для обхода FK. Общий M:N editor не меняет архивный проект; чтение
связей и подтверждение ранее принятой проекции — отдельные metadata операции.

Архив запрещает новые execution starts независимо от восстановления пространства.
Он не объявляет существующий job terminal и не заменяет подтверждённый Space drain.
Контрольные/terminal receipts классифицируются отдельно от контентных изменений;
полный V3 machine/grant протокол ещё требует реализации и qualification.

В новом, ещё не опубликованном ProjectSpaceReadContext lifecycle привязан к тому
же точному ProjectRef, что links. Строгие прежние ExecutionContextV1/V2 не меняются.
Все потребители нового context должны поставляться совместимым cohort.
