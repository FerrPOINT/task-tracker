# Единые стадии и статусы задач

Статус: согласованный контракт; реализация и приёмка не завершены.

Tracker владеет единственным состоянием задачи. Все проекты и типы задач
используют Draft, Backlog, Analysis, Architecture, Development, Review, Testing,
Rework, Deployment и Ready/InProgress/Completed. Колонки доски — стадии.
Ожидание, блокировка и наличие запущенного процесса не являются статусами.

Девять стадий обязательны по умолчанию, включая пустые проекты без namespace.
Чистая установка активирует пустую модель автоматически и сохраняет свой ID.
Заполненная установка требует одного согласованного переноса после готовности
writers; это технический барьер, а не opt-in проекта или frontend build flag.

Новая задача атомарно получает Draft/Ready без обращения к Fleet/Workflow.
Ручная и агентная команды используют общий переход, ревизию и аудит.
Ручной автор не создаёт квитанций агента. Активное или неизвестное исполнение
блокирует конфликтующие ручные переходы; истечение lease не означает остановку.

Основная последовательность: Draft → Backlog → Analysis → Architecture →
Development → Review → Testing → Deployment. Завершение этапа переводит
следующий этап в Ready; Deployment завершается Completed. Review/Testing
могут вернуть в Rework, завершение Rework переводит в Review. Повторное
открытие Deployment/Completed переводит в Rework/Ready.

Категории совместимой проекции: todo для Draft/Backlog в Ready, done только
для Deployment/Completed, остальные сочетания — in_progress. Старые строгие
контракты SDLC и исторические receipts сохраняются. Политика пространств
и человеческий доступ к приложениям не переключаются этой поставкой.

## Миграция

| Старое состояние | Новая стадия | Новый статус |
| --- | --- | --- |
| To Do | Backlog | Ready |
| In Progress | Development | InProgress |
| Review | Review | Ready |
| Done | Deployment | Completed |

Достоверное существующее SDLC-состояние имеет приоритет. Исторический
Clarification отображается как Draft/уточнение. Неизвестное или противоречивое
состояние блокирует соответствующий пакет; угадывание по произвольному имени
запрещено. UUID, ключи, авторы, содержимое, связи и история сохраняются.
Перенос Done означает Deployment/Completed по решению пользователя, но не
создаёт задним числом процесс, deployment receipt или успешную проверку.

## Поставка и приёмка

Последовательность: owner core/миграции → UI/CLI → Fleet/Workflow → Base
Compose/Kubernetes adapters → заполненная migration/replay/rollback QA → dev
установка и IAB → зависимые PR и отдельный production-пакет. Production write
требует отдельного поручения; этот контракт его не разрешает.

Обязательны проверки конфликтов ревизий, повторов, гонок назначения с ручным
переходом, сохранности данных, категорий/счётчиков, отсутствия пропавших карточек,
прямых API/CLI, отказов Auth/Fleet/Workflow, SSE с API prefix, реальной передачи
агенту текущего этапа, Rework/stop/recovery, Compose/Kubernetes и IAB375/1920/2560.
Браузерные и runtime результаты не подменяются unit-тестами.

## Явный вход человека в агентное исполнение

Новый command/receipt handoff имеет отдельную строгую схему. Клиент не передаёт
целевую стадию, автора или previous agent result: сервер берёт текущую стадию из
заблокированного состояния. Команда подтверждает актуальные issue inputs по hash,
ревизию задачи, версию routing и введённый человеком RequirementsDocument.
Его автором остаётся реальный человек; это не результат PM или прошлых агентов.

Исторические strict envelopes не расширяются. Гарантии frozen input, owner consent,
assignment и fencing сохраняются; новый entry basis проверяется явно. Старые
creation/completion receipts нельзя генерировать ради прохождения прежних guards.
Подтверждение handoff ещё не означает запуск: запуск подтверждается настоящими
Fleet/Workflow assignments и их readback. Неизвестная судьба запроса не освобождает
владение по таймеру. Rollback сохраняет явный basis и историю.

Workflow выбирает entry point текущей стадии в закреплённой версии режима;
пропущенные вручную стадии не отмечаются как выполненные агентом. Основной
configured-cli-v1 и реальные сообщения/outbox используются повторно. Этот путь
имеет проверенную границу подготовки и атомарного сохранения настоящих human
materials. HTTP/outbox/consumer adapters и живая проверка ещё не завершены;
сохранение согласия не является фактическим запуском.
