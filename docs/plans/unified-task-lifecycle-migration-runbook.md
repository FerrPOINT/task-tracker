# Перенос единого lifecycle: runbook кандидата

Статус: **не квалифицирован для установки**. Документ относится к согласованному
[плану](unified-task-lifecycle-20261030.md). Ниже обязательные условия будущей
поставки; наличие SQL-функции не разрешает активировать рабочую установку.

## Предварительные условия

1. Подтвердить origin, host, installation и storage. Работа в PDLC4 выполняется
   на Firebat2; production требует отдельного явного поручения.
2. Зафиксировать SHA исходников, независимые SDK/UI pins, точные images и writers:
   Tracker HTTP/CLI, Fleet, Workflow и detached consumers. Все обслуживающие writers
   должны понимать новую модель и явный current-stage handoff.
3. Подготовить и проверить совместимый rollback cohort, сохранив прежние images.
   После активации старый writer без lifecycle admission использовать нельзя.
4. Создать согласованные backup БД и файлов, сохранить receipt и проверить чтение.
   Backup, inventory и журналы остаются в защищённом каталоге выбранного host.
5. Остановить новые агентные назначения, подтвердить drain текущих по реальным
   owner receipts. Lease timeout и отсутствие процесса сами по себе не подтверждают
   завершение; unknown effects согласуются по исходным operation keys.

## Репетиция на заполненных изолированных данных

Проверить четыре неизменных baseline UUID, реальные старые SDLC/Clarification,
удалённые задачи, документы/вложения, комментарии, worklogs, связи и историю.
Применить только аддитивные миграции. Снять `task_lifecycle_inventory_snapshot()`.
Сохранить до/после UUID/ключи и hashes пользовательских полей отдельно от проекции.
Неизвестные статусы, несогласованный parent/execution state и незавершённые
исполнения блокируют пакет; значения по имени не угадываются.

Активация повторно сверяет точный inventory под writer barrier и переносит пакет
одной транзакцией. Изменившийся inventory требует новой проверки. Ошибка в середине
не оставляет частичного state/history/events/control. Повтор не дублирует импорт.
Старое Done становится Deployment/Completed без запуска реальной выкладки.

Проверить создание обычной задачи/подзадачи Draft/Ready без Fleet и Workflow,
ручные переходы с CAS/idempotency, конкуренцию с назначением и WIP, категории и
pagination, недоступность старых writers и право реального автора. Отдельно
проверить неизвестную судьбу запроса и повтор чтения результата.

## Чистая установка и ручное владение

Core identity принадлежит модели задач. На действительно новой БД Tracker
сохраняет созданный UUID, если оператор не задал явный ID, и автоматически
включает пустую модель после миграций. Повторный запуск сохраняет ID; несовпадение
явного ID запрещено. Существующая пустая установка не считается новой и требует
проверки совместимого cohort. Настройки исполнения не включают/выключают стадии.

Перед первыми миграциями сервер под advisory lock сохраняет `bootstrap_id` в
`task_model_bootstrap_provenance` только после проверки отсутствия прежней схемы
Tracker. Признак pending переживает прерывание процесса и миграций. Повторный
старт продолжает тот же bootstrap; активация и завершение provenance выполняются
одной транзакцией. Если за время прерывания появились задачи, empty-bootstrap
отказывает и требует сверки оператором; данные не очищаются.

Существующая схема, даже пустая, не получает provenance задним числом. Миграция114
создаёт на ней только пустую таблицу. Наличие таблицы или заданного instance ID
не даёт права автоматически включить модель; подделывать pending для обхода
cohort/inventory запрещено. Завершённая запись остаётся историей первого запуска.

Старое завершённое назначение не означает активное выполнение. Ручная передача
владения проверяет реальные terminal/confirmation receipts и отсутствие holds
под блокировкой задачи. Lease timeout не освобождает её. Перед первым ручным
изменением сохраняются точные прежние state и execution head в неизменяемой
истории custody; агентные квитанции не переписываются и не создаются.
Текущая execution-проекция отделяется от ручного состояния, старый writer не
может продолжить её без нового явного handoff. Авторизация, fencing и admission
сохраняются. Эти условия требуют отдельных положительных и отрицательных тестов.

## Dev-поставка и приёмка

Сначала установить совместимый cohort без активации; сравнить фактически
обслуживаемые images/flags с qualification receipts. Затем выполнить owner import
и включить UI только после успеха. Роли, приложения и пространство не переключать.

Проверить Compose и Kubernetes отдельно, два пользователя/две вкладки, SSE на
фактическом API prefix и исходном сроке допуска, экраны 375/1920/2560 px, ручную
работу при недоступном исполнителе. Явная передача текущего этапа, Rework, остановка
и восстановление подтверждаются реальным Fleet/Workflow-заданием.

В завершение сверить сохранность данных, runtime health, сервисные связи и
нетронутые соседние ресурсы. Отчёт отдельно фиксирует source, scoped checks,
миграционную репетицию, образы, dev приёмку и ограничения hosted CI.

## Rollback и production-пакет

Rollback сохраняет новые связи, lifecycle, ревизии и аудит; используются только
совместимые images. Destructive down-migration и обнуление control не допускаются.
Репетиция rollback обязательна до dev активации. Восстановление backup — отдельная
аварийная процедура с учётом более новых данных, не обычная смена образа.

Production-пакет содержит проверенные immutable artifacts, backup/inventory/drain
процедуры, qualification receipts, точную последовательность и rollback. Его
подготовка не является production-поставкой. Текущий кандидат ещё не прошёл все
перечисленные условия; выполнять установку по этому документу сейчас нельзя.
