# Декомпозиция: дизайн в карточке Tracker

Статус: дизайн в настоящем frontend Tracker, 2026-11-03. Утверждение дизайна ожидается.
План этапа согласован пользователем; это не утверждение ещё не показанного интерфейса.
Общий процесс: [Base PR 444](https://github.com/FerrPOINT/services-base/pull/444).

## Сценарий и навигация

В карточке одной задачи вкладка «Декомпозиция» находится перед SDLC.
Описание задачи и остальные вкладки сохраняются. URL хранит выбранную вкладку;
ссылка на раздел открывает его по стабильному ID. Раздел — часть плана без
собственного назначения, Workflow, чата, ветки или поставки.
Прямая ссылка доступна как иконка справа от названия раздела, в том числе когда
он свёрнут. У ссылки есть доступное имя и подсказка; это отдельный элемент рядом
с раскрытием, без текстовой кнопки внизу содержимого. Ссылка поддерживает обычные
действия браузера, включая открытие в новой вкладке и копирование адреса.

Шапка плана: редакция, автор, требования и «Редактировать». Номер редакции
открывает прежние версии плана и причины изменений; отдельной кнопки «История»
нет. Общая лента активности задачи сохраняет своё назначение; дополнительная
вкладка истории для плана не создаётся.
Общая архитектурная часть и упорядоченные разделы свёрнуты по умолчанию.
Прямая ссылка раскрывает только указанный раздел, остальные остаются свёрнутыми. Каждый отвечает
на вопросы «Что сделать» (с ожидаемым результатом), «Как проверить» и
«Какие требования покрывает». По замечанию владельца убраны статусы выполнения,
счётчик N/M и действия отметки: декомпозиция описывает работу, а её фактическое
выполнение и независимая приёмка отражаются в существующем SDLC всей задачи.

Человек с правами задачи может редактировать план. При активном
изменяющем назначении или отсутствии права — только чтение с причиной.
В форме доступны добавление, удаление, перемещение вверх/вниз, явные «Сохранить» и «Отмена»
и причина изменения сохранённого плана. Первое создание не требует отдельной
причины; сохранение без изменений не создаёт редакцию. Отмена возвращает
сохранённое содержание и порядок. Черновик остаётся в памяти между вкладками; уход с него
требует решения пользователя. Смена сценария демонстрации подчиняется тому же guard.

Ошибка сохранения плана не очищает поля и позволяет повторить запись.
Редакции — просмотр снимков без восстановления; их разделы также свёрнуты
по умолчанию. При конфликте текущая редакция
и локальная правка видны раздельно; продолжение явно меняет базовую редакцию,
но ничего не сохраняет до повторного Save.

## Контракт владельца

| Операция           | Требуемое поведение                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------ |
| Прочитать план и историю   | Доступ задачи, редакция требований, стабильные section IDs; история снимков                |
| Сохранить содержание плана | Атомарно весь план и порядок разделов; ожидаемая редакция, актуальные требования, причина правки сохранённого плана, права/assignment guards и история |
| Сверить исход сохранения | Readback исходной операции и содержимого после timeout; повтор принятой записи возвращает тот же результат, а не новую редакцию |

Права, требования и изменяющее назначение проверяются при самой записи.
Неизвестный исход сохраняет черновик и не показывается как успех; новый номер
редакции сам по себе не подтверждает принятие этой операции. Поздний ответ
не очищает более новую правку и не восстанавливает доступ после его отзыва.
Отдельных операций отметки выполнения или записи результата раздела нет:
результат Developer и независимая приёмка относятся к существующему отчёту задачи.

Историческая ссылка связывает редакцию плана и стабильный ID раздела. Удалённый
раздел остаётся доступен в прежней редакции. Ссылка на отсутствующий раздел
текущего плана показывает причину и доступную историю, без подстановки другого
раздела. Production использует URL раздела со стабильным UUID; выбранная редакция читается отдельным owner API.

Preview `model.ts` содержит только типы вымышленных fixtures. Production DTO
генерируются из Rust/OpenAPI, а постоянное хранение, API и CLI описывает
[контракт управления](../contracts/task-decomposition.md). Он не меняет
Workflow/Advisor и не добавляет автоматическое принятие плана.

## Дизайн в существующем приложении

По требованию владельца отдельная копия карточки и её HTML/Vite entry удалены.
Вкладка встроена в настоящий `IssueDetailPage`: исходные AppShell, меню проекта,
описание, поля, ссылки, время, участие и соседние вкладки переиспользуются.
Разметка страницы не дублируется. Контроллер плана передаётся в существующую
карточку; панель остаётся смонтированной при переключении вкладок для сохранения
черновика и защиты ухода. При переходе к другой задаче её состояние сбрасывается.

Для локального просмотра используются штатный Vite и dev-порт workspace 6173:

```powershell
$env:VITE_DECOMPOSITION_DESIGN = 'true'
$env:VITE_API_BASE_URL = 'http://localhost:8721/api/v1'
$env:VITE_AUTH_ISSUER = 'http://localhost:8701'
$env:VITE_AUTH_CLIENT_ID = 'task-tracker-dev'
pnpm dev --host 127.0.0.1 --port 6173 --strictPort
```

[Карточка SDLC2-1](http://localhost:6173/issues/SDLC2-1?tab=decomposition).
Порты API/Auth взяты из существующего SDLC2; другие workspace используют свою
конфигурацию. Авторизация и данные самой задачи проходят штатные клиент и API.
Кнопка «Требования задачи» открывает её настоящий SDLC, сохраняя черновик.
В исходном dev-примере план и правки остаются
демонстрационными, в памяти; в панели это обозначено явно. Для обзора дизайна показан подробный пример настроек уведомлений из шести
разделов: хранение, права, форма, доставка, восстановление после ошибок и общая
проверка. Это демонстрационный план, а не архитектурный результат текущей задачи.
Однораздельный пример сохранён среди unit fixtures.

Дизайн-контроллер подключается только при `import.meta.env.DEV` и явном флаге.
Обычная production-сборка исключает его и fixtures, подключая в той же вкладке
постоянный контроллер owner API (см. контракт управления ниже). Пример не
подменяет результат API и не обходит авторизацию. Публикация исходников и
изменение pinned runtime images — отдельные проверки.
Старый сервер отдельного макета на 4186 остановлен.

Unit fixtures дополнительно покрывают пустой/одиночный/длинный план, loading,
read error, readonly, active agent, conflict, stale requirements, save error и
отзыв доступа. Конфликт и отказ записи эмулируются только в контроллере плана,
без подмены API Tracker или выдачи фиктивных серверных результатов за настоящие.

## Приёмка и утверждение

Проверить правку/порядок/отмену, draft между вкладками, leave guard и
отказ записи, историю, конфликт, deep links, Back/Forward, клавиатуру и фокус.
Отдельно проверить первое создание без причины, правку с причиной, сохранение
без изменений, ссылку на удалённый раздел, unknown outcome и поздний ответ
после нового ввода или отзыва доступа. Эти пункты задают целевое поведение;
их наличие в документе не означает, что текущий design-контроллер уже их реализует.
Браузер: 375/768/1920/2560, три темы, длинный контент, отсутствие записи демонстрационного плана в реальные API, переполнения документа и недоступных действий.
Доказательства привязываются к точному commit. Статус до явного ответа владельца:
**не утверждено**. Хранение плана, API/agents и rollout остаются отдельным этапом.
После явного утверждения конкретной версии и сценариев готовится отдельный план
реализации Tracker, Workflow и инструкций агентов с unit- и PostgreSQL-тестами.

Пустые метаданные карточки (метки, поля, связи) показываются короткими подписями,
без отступов страничного EmptyState. Действия добавления меток и связей стоят
рядом с заголовком. Пустота подтверждается успешным чтением; loading/error и ACL
сохраняют прежнее поведение, ошибка не подменяется пустым состоянием.

На узком экране свойства задачи свёрнуты в одну строку «Детали · текущий статус»;
раскрытие показывает статус, приоритет, исполнителя и спринт по два поля в ряду.
На desktop свойства открыты справа. Для выбора используется штатный Select Base,
а не локальное меню: состав вариантов, права, блокировка на время сохранения и
API записи сохраняются. Статус в свёрнутой строке берётся из общего каталога по ID,
как и в поле. Во время недоступности справочника пользователей выбор исполнителя
заблокирован, при ошибке доступен повтор чтения.

Вкладки используют underline-представление Base, одну строку и горизонтальную
прокрутку при нехватке места; активная вкладка остаётся видимой при переходе и
изменении размера окна. Кнопка изменения заголовка находится в его строке.
Прокручиваемая область оставляет место для внешней рамки фокуса Base со всех
сторон; раскрытие вкладки у края учитывает этот отступ, не обрезая индикатор.
Редакция и действия плана сгруппированы, отдельный повтор заголовка вкладки убран.
Метки, поля, связи, учёт времени и участие используют прозрачные компактные секции
Base без лишних Card. Минимальные области нажатия 40/44 px сохраняются.
Это применение существующих правил Base, а не новый локальный пресет плотности.


## Управление планом и CLI

По следующему запросу владельца подготовлена реализация постоянного управления
планом и CLI: [контракт](../contracts/task-decomposition.md). Это отдельный
функциональный этап, не объявление визуального дизайна утверждённым. Production
вкладка использует owner API, dev-флаг по-прежнему открывает вымышленные примеры.
Workflow/Advisor и их оценка не изменяются, готовность полного SDLC не заявляется.
