# Обсуждение задачи и результат стадии

Для `single-task-v1` каждая профессия читает задачу и обсуждение участников,
выполняет работу, сохраняет итоговый комментарий и передаёт typed результат.
Комментарий — обычная запись `comments`, видимая существующему интерфейсу.
Автор — собственный локальный пользователь исполнителя, найденный по проверенному
`central_sub`; владелец задачи не подставляется как автор.

## API и CLI

Все маршруты находятся под существующим strict Central Auth SDLC router:

| Метод и путь после `/api/v1/issues/{task}/sdlc` | CLI после `task-tracker sdlc` | Назначение |
| --- | --- | --- |
| `GET /discussion` | `discussion read --task UUID` | Title/description и страница обсуждения |
| `POST /discussion` | `discussion publish --task UUID --from-file FILE` | Сохранение итогового комментария |
| `GET /discussion/operations/{key}` | `discussion operation --task UUID --key KEY` | Проверка исходной операции и реального комментария |

Чтение требует ровно одного собственного PM или Delivery task grant и
`task-tracker:read`. Запись дополнительно требует `task-tracker:write`.
Generic credentials, человеческая сессия, смесь grants, чужая задача и
неразрешённые дополнительные scopes не дают доступа. Сохраняются проверки
свежих project/account ACL, текущего назначения, профиля, lease и runtime.
Отключение допуска **новых** single-task назначений не отменяет запись/чтение
обсуждения по уже действующему назначению: оно должно иметь возможность сохранить
итог и завершиться. Свежие ACL, текущий grant, binding и живая lease проверяются
и в этом случае. Новое назначение при отключённом допуске не выдаётся.

## Полное обсуждение

`limit` — от 1 до 500, по умолчанию 100. Ответ содержит `snapshot` — верхний
comment ID первого запроса, и `next_after`. Пока `next_after` не `null`, следующий
запрос передаёт этот ID как `after` и исходный `snapshot`. Порядок определяется
`(created_at,id)`; offset не используется. Cursor проверяется на той же задаче;
удалённый cursor вызывает conflict и требует нового сканирования. Новые записи
после snapshot читаются новым сканированием перед завершением работы.

Читаются все участники, а не только последний автор или текущая профессия.
Пустое обсуждение имеет пустой массив и `next_after=null`. Названия и описание
возвращаются из настоящей задачи, а не восстанавливаются из отчёта агента.

## Комментарий и fence

`PublishStageComment` содержит только `body`, `fence`, `idempotency_key`.
Непустое тело сохраняет Unicode и переносы, максимум 100000 символов, без NUL.
Это содержательный отчёт: выполненная работа, exact inputs/candidate, реальные
проверки/evidence, findings/ограничения и запрошенные следующие stage/status.
Текст не должен выдавать ещё не выполненный переход за принятый результат.

Для PM `fence` имеет `kind="pm"`, настоящий `MachineFence`, `lease_id` и
`expected_lease_version`. Для остальных — `kind="delivery"` и действующий
`DeliveryFence`. Значения выдаются текущими контрактами назначения/аренды.
Тело не может назначить автора, owner, project, роль или произвольный статус.

Fleet выдаёт текущему run `FLEET_STAGE_COMMENT_KEY`. После первого POST ключ и
тело заморожены. Exact replay возвращает тот же comment ID без новой записи;
изменённое тело под тем же ключом отклоняется. Неопределённый ACK сначала
согласуется через исходную operation. Возвращаемый `body_sha256` относится к
UTF-8 телу комментария, не ко всему JSON-файлу команды.

Operation проверяет сохранённые task/author/assignment/execution и настоящий
комментарий. Удалённая или изменённая запись вызывает conflict. Исторический
replay не создаёт новую запись и требует первоначальный точный grant и свежий
project/account ACL. Он не предоставляет новое право чтения всей дискуссии.

Комментарий и receipt операции сохраняются в одной task-locked транзакции:
используются существующие `comments` и `sdlc_idempotency`, без нового хранилища
сообщений. После commit HTTP-граница вызывает существующую службу уведомлений
и SSE для первоначальной записи. Это best-effort уведомление, не отдельное
доказательство commit; replay не дублирует уведомления.

## Завершение стадии

Новая техническая proposal и фактический guarded Complete требуют сохранённого
комментария того же producer/task/assignment/execution и текущей редакции
требований. Проверяется настоящее тело, а не только JSON receipt. Повторная
проверка при Complete защищает от удаления/изменения после proposal.
PM completion проверяет комментарий текущего PM и exact revision; consent
владельца и все прежние guards остаются отдельными условиями.

Агент сохраняет и проверяет комментарий **после принятия** финального Workflow report.
Workflow оценивает уже существующий результат и подготовленное резюме, не
собственную будущую квитанцию или ещё не опубликованный комментарий.
Technical role отправляет typed proposal при живом run. Fleet после настоящего
native terminal выполняет guarded переход. Агенту не даются scheduler или
generic issue-transition полномочия. Проверяется реальный stage/status readback.

Команды и инструкции требуют совместного обновления Tracker CLI/API, Fleet и
Workflow profile hashes. Старые профили/исторические receipts не переписываются;
новые проверки не пересоздают прежние эффекты при replay. Source, unit,
PostgreSQL/HTTP qualification и live-приёмка — отдельные этапы.
